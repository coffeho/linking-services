# Архитектура HR System

## 1. Общая идея архитектуры

HR System постепенно переносится из монолитного файла `main.py` в структурированный учебный проект.

Изначально в одном файле находились:

- Tkinter GUI;
- подключение к SQLite;
- создание таблиц;
- начальные данные;
- авторизация;
- сотрудники;
- подразделения;
- должности;
- отпуска;
- приказы;
- переводы;
- отчеты.

Главная архитектурная цель проекта — отделить запускаемую часть приложения от переиспользуемой логики.

Текущий принцип разделения:

```text
app/ui/main_window.py       запускаемая часть и Tkinter GUI
main.py                     тонкая совместимая обёртка
packages/core/*             переиспользуемые модули HR-системы
tests/*                     автоматические проверки
docs/*                      проектная документация
scripts/* и Makefile        автоматизация команд
```

## 3. Основные части системы

### `app/ui/main_window.py`

`app/ui/main_window.py` является основным запускаемым Tkinter-слоем приложения.

Он отвечает за:

- создание Tkinter-окна;
- отображение экранов;
- обработку действий пользователя;
- показ сообщений;
- вызов core-модулей.

На текущем этапе файл всё ещё содержит большую часть Tkinter-интерфейса. Отдельные формы пока не разделены по самостоятельным файлам.

### `main.py`

Корневой `main.py` теперь является тонкой совместимой обёрткой.

Он импортирует `main()` и `HRSystemApp` из:

```text
app/ui/main_window.py
```

Также `main.py` экспортирует `Database` для сохранения совместимости со smoke-тестами.

Старый запуск продолжает работать:

```bash
python main.py
```

Основной запуск через Makefile выполняется командой:

```bash
make run
```

Она запускает приложение через:

```bash
python -m app.ui.main_window
```

### `packages/core`

`packages/core` — переиспользуемое ядро системы.

На текущем этапе в него вынесены:

- `storage.py` — класс `Database`, создание таблиц и начальные данные;
- `auth.py` — авторизация и хеширование паролей;
- `models.py` — доменные модели HR-системы;
- `employees.py` — операции сотрудников;
- `departments.py` — операции подразделений;
- `positions.py` — операции должностей;
- `vacations.py` — операции отпусков;
- `transfers.py` — операции переводов;
- `reports.py` — операции формирования отчетов.

Если `orders.py` уже присутствует в `packages/core`, он отвечает за операции кадровых приказов.

Код внутри `packages/core` должен быть пригоден для тестирования без запуска GUI.

### `tests`

Тесты разделены на группы:

- `tests/smoke/` — фиксируют базовое поведение исходного монолита;
- `tests/unit/` — проверяют core-логику отдельно от интерфейса.
- `tests/integration/` — проверяют совместную работу нескольких core-модулей и временной SQLite-базы.

Smoke-тесты защищают поведение, которое существовало до рефакторинга. Unit-тесты проверяют уже вынесенные core-модули.

### `docs`

Папка `docs` содержит проектную документацию:

- `index.md` — главная страница документации;
- `specification.md` — спецификация системы;
- `domain.md` — описание предметной области;
- `architecture.md` — архитектурное описание;
- `team.md` — разделение обязанностей в команде.

Документация собирается через MkDocs командой:

```bash
make docs
```

### `Makefile` и `scripts`

`Makefile` является единой точкой запуска повторяющихся команд:

```bash
make help
make setup
make run
make test
make smoke-test
make auth-test
make coverage
make docs
make clean
make integration-test
```

Скрипты в папке `scripts/` содержат команды, которые вызываются из `Makefile`.

Это сделано для того, чтобы разработчик и проверяющий запускали проект одинаковыми командами, а не собирали длинные команды вручную.

## 4. Граница между GUI и core

Текущая граница проходит так:

```text
app/ui/main_window.py
        ↓
packages/core/auth.py
packages/core/storage.py
packages/core/models.py
packages/core/employees.py
packages/core/departments.py
packages/core/positions.py
packages/core/vacations.py
packages/core/transfers.py
packages/core/reports.py
        ↓
SQLite
```

Если модуль `orders.py` уже добавлен, он также находится между GUI и SQLite как часть `packages/core`.

GUI отвечает за:

- ввод данных пользователем;
- кнопки;
- таблицы;
- окна;
- сообщения об ошибках и успехе.

Core отвечает за:

- авторизацию;
- модели предметной области;
- операции сотрудников;
- операции подразделений;
- операции должностей;
- операции отпусков;
- операции переводов;
- формирование данных для отчетов;
- инициализацию базы данных через текущий `storage.py`.

Важное правило:

```text
packages/core не должен импортировать Tkinter
```

Проверка:

```bash
grep -R "tkinter" packages/core || true
```

Ожидаемый результат — команда ничего не выводит.

## 5. Основные потоки взаимодействия

### Запуск приложения

```text
make run
        ↓
scripts/run.sh
        ↓
python -m app.ui.main_window
        ↓
app/ui/main_window.py создает Tkinter-окно
        ↓
HRSystemApp инициализирует Database
        ↓
пользователь работает с GUI
```

Старый запуск также остаётся доступным:

```bash
python main.py
```

В этом случае `main.py` вызывает `main()` из `app/ui/main_window.py`.

### Авторизация

Текущий поток авторизации:

```text
Пользователь вводит логин и пароль
        ↓
app/ui/main_window.py получает значения из Tkinter Entry
        ↓
app/ui/main_window.py вызывает authenticate_user(cursor, login, password)
        ↓
packages/core/auth.py хеширует пароль
        ↓
packages/core/auth.py ищет пользователя в SQLite
        ↓
возвращается AuthenticatedUser или None
        ↓
app/ui/main_window.py показывает успех или ошибку
```

После выноса авторизации GUI больше не знает деталей хеширования пароля.

### Инициализация базы данных

Текущий поток инициализации базы данных:

```text
Запуск приложения
        ↓
создается HRSystemApp
        ↓
создается Database из packages/core/storage.py
        ↓
Database подключается к SQLite
        ↓
Database создает таблицы
        ↓
Database добавляет демонстрационные данные, если база пустая
```

Это поведение защищено smoke-тестами.

## 6. Известные ограничения текущей версии

Текущая архитектура является промежуточной.

Ограничения:

- `app/ui/main_window.py` пока остается большим файлом;
- отдельные Tkinter-формы еще не разделены по файлам;
- `main.py` является совместимой обёрткой, но всё ещё нужен для старого запуска и smoke-тестов;
- `storage.py` пока находится внутри `packages/core`;
- нет отдельного слоя `app/adapters`;
- контейнеризация пока не добавлена;
- core пока не оформлен как устанавливаемый Python-пакет через `pyproject.toml`;
- диаграммы будут добавлены отдельным шагом позже.

Причина, почему `storage.py` сейчас находится в `packages/core`: на этом этапе главная цель — убрать создание базы и начальную загрузку данных из запускаемого слоя. В дальнейшем слой хранения может быть вынесен в отдельный адаптер.

    ├── auth.py

Каждый шаг должен сохранять прохождение smoke-тестов и unit-тестов.

## 8. Проверка архитектурных правил

Основная проверка проекта:

```bash
make test
```

Ожидаемый результат зависит от текущего количества тестов, но все тесты должны проходить.

Проверка отсутствия Tkinter в core:

```bash
grep -R "tkinter" packages/core || true
```

Ожидаемый результат:

```text
команда ничего не выводит
```

Проверка smoke-тестов:

```bash
make smoke-test
```

Проверка unit-тестов авторизации:

```bash
make auth-test
```

Сборка документации:

```bash
make docs
```

## 9. Связь с требованиями проекта

Текущая архитектура уже частично закрывает требования:

- исходный монолит сохранен в истории Git;
- добавлены smoke-тесты перед рефакторингом;
- создано начало `packages/core`;
- авторизация вынесена из GUI-кода;
- добавлены доменные модели;
- часть бизнес-логики вынесена в core-модули;
- добавлены unit-тесты core-логики;
- добавлен Makefile как единая поверхность команд;
- добавлена автоматическая сборка документации;
- запускаемый Tkinter-слой вынесен в `app/ui`.
- добавлен integration-тест кадрового сценария увольнения через приказ;
