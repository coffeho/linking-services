# Разделение обязанностей в проекте

## 1. Участники проекта

Проект выполняется в паре.

В работе используются две роли:

- разработчик;
- reviewer.

Такой формат нужен, чтобы проект развивался не как личная папка с кодом, а как общий инженерный артефакт, который можно проверить, обсудить и воспроизвести.

## 2. Роль Ульяны Ишумбаевой

Ульяна отвечает за техническую часть проекта.

Зоны ответственности:

- перенос исходного HR-монолита в Git;
- работа с ветками и Pull Request;
- добавление smoke-тестов базового поведения;
- вынос `Database` в `packages/core/storage.py`;
- вынос авторизации в `packages/core/auth.py`;
- добавление unit-тестов авторизации;
- добавление доменных моделей в `packages/core/models.py`;
- добавление unit-тестов моделей;
- настройка `Makefile` и `scripts`;
- проверка команд проекта;
- контроль того, что `packages/core` не зависит от Tkinter.

Выполняемые проверки:

```bash
make test
make smoke-test
make auth-test
make coverage
```

## 3. Роль Олега Ратовского

Напарник отвечает за review, документационную часть проекта и проверку понятности проекта для другого человека.

Зоны ответственности:

- проверка Pull Request перед merge;
- запуск команд проверки;
- комментарии в Pull Request;
- проверка понятности README;
- участие в подготовке документации;
- проверка описания предметной области;
- проверка архитектурного описания;
- подготовка или проверка диаграмм на следующих этапах;
- контроль того, что термины в документации совпадают с терминами в коде;
- участие в настройке автоматической сборки документации;
- проверка команды сборки документации после её добавления.

После добавления автоматической сборки документации напарник должен проверять команду:

```bash
make docs
```

Ожидаемый результат — документация собирается без ручного редактирования сгенерированных файлов.

Пример review-комментария:

```text
Проверил PR. Команды запускаются, тесты проходят, документация понятна, замечаний нет. Можно мержить.
```

## 5. Правила работы через Pull Request

Для каждой логической задачи создается отдельная ветка.

Примеры веток:

```text
test/add-smoke-baseline
refactor/extract-storage
refactor/extract-auth
test/add-auth-unit-tests
docs/add-project-specification
docs/add-core-documentation
docs/add-team-responsibilities
```

В Pull Request указывается:

- что изменено;
- зачем это сделано;
- как проверялось;
- какие команды запускались.

Перед merge reviewer должен проверить изменения и оставить комментарий.

## 6. Проверка перед merge

Минимальная проверка перед merge:

```bash
make test
```

Если изменение связано с конкретной частью проекта, запускается дополнительная проверка.

Например:

```bash
make smoke-test
make auth-test
python -m pytest tests/unit/test_models.py -v
```

Если изменение связано с документацией, проверяются:

```bash
make test
```

А после добавления сборки документации также будет проверяться:

```bash
make docs
```

## 7. Текущее состояние командной работы

На текущем этапе уже использовались:

- отдельные ветки;
- Pull Request;
- review-комментарии;
- merge в `main`;
- локальные проверки перед merge.

Это соответствует требованию проекта вести работу через Git-историю, ветки, Pull Request и review.

## 8. План по документации

Документация развивается постепенно.

Уже добавлены или планируются:

- `README.md` — точка входа в проект;
- `docs/specification.md` — спецификация HR-системы;
- `docs/domain.md` — описание предметной области;
- `docs/architecture.md` — архитектурное описание;
- `docs/diagrams/` — редактируемые диаграммы;
- автоматическая сборка документации через отдельную команду.

Ответственность напарника в этом блоке — следить, чтобы документация была понятной, не устаревала относительно кода и могла быть собрана автоматизированной командой.
