# Спецификация HR System

## 1. Назначение системы

HR System — учебное desktop-приложение для кадрового учета организации.

Система предназначена для хранения и просмотра кадровых данных, а также для выполнения базовых кадровых операций:

- авторизация пользователей;
- просмотр и управление сотрудниками;
- учет подразделений;
- учет должностей;
- учет отпусков;
- создание и исполнение кадровых приказов;
- оформление переводов между подразделениями;
- просмотр отчетов и статистики.

## 2. Роли пользователей

### Администратор

Администратор имеет максимальные права.

Он может:

- входить в систему;
- просматривать сотрудников;
- добавлять, изменять и удалять сотрудников;
- управлять подразделениями;
- управлять должностями;
- работать с отпусками;
- создавать и исполнять приказы;
- оформлять переводы;
- просматривать отчеты;
- управлять пользователями.

### HR-менеджер

HR-менеджер работает с кадровыми данными.

Он может:

- входить в систему;
- просматривать сотрудников;
- добавлять и изменять сотрудников;
- работать с подразделениями и должностями;
- оформлять отпуска;
- создавать и исполнять кадровые приказы;
- оформлять переводы;
- просматривать отчеты.

### Бухгалтер

Бухгалтер имеет доступ к кадровым данным, связанным с зарплатой и отчетами.

Он может:

- входить в систему;
- просматривать сотрудников;
- просматривать должности;
- просматривать отчеты.

### Сотрудник

Сотрудник является базовой ролью.

В текущей версии пользователь с ролью сотрудника может войти в систему, но доступ к административным разделам ограничен.

## 3. Основные сущности

### User

Пользователь системы.

Поля:

- `user_id` — идентификатор пользователя;
- `login` — логин;
- `password` — хеш пароля;
- `role` — роль пользователя;
- `full_name` — полное имя;
- `active` — признак активной учетной записи.

Ограничения:

- логин должен быть уникальным;
- неактивный пользователь не должен получать доступ к основному экрану.

### Employee

Сотрудник организации.

Поля:

- `employee_id` — идентификатор сотрудника;
- `last_name` — фамилия;
- `first_name` — имя;
- `middle_name` — отчество;
- `birth_date` — дата рождения;
- `hire_date` — дата приема;
- `department_id` — подразделение;
- `position_id` — должность;
- `salary` — зарплата;
- `status` — статус сотрудника.

Поддерживаемые статусы:

- `Работает`;
- `Уволен`;
- `В отпуске`;
- `На больничном`.

### Department

Подразделение организации.

Поля:

- `department_id` — идентификатор подразделения;
- `department_name` — название подразделения;
- `manager_id` — руководитель подразделения.

Ограничения:

- подразделение нельзя удалить, если в нем есть сотрудники.

### Position

Должность.

Поля:

- `position_id` — идентификатор должности;
- `position_name` — название должности;
- `base_salary` — базовая зарплата.

Ограничения:

- должность нельзя удалить, если на ней есть сотрудники.

### Vacation

Отпуск сотрудника.

Поля:

- `vacation_id` — идентификатор отпуска;
- `employee_id` — сотрудник;
- `start_date` — дата начала;
- `end_date` — дата окончания;
- `vacation_type` — тип отпуска.

Ограничения:

- дата окончания отпуска не должна быть раньше даты начала.

### Order

Кадровый приказ.

Поля:

- `order_id` — идентификатор приказа;
- `order_type` — тип приказа;
- `order_date` — дата приказа;
- `employee_id` — сотрудник;
- `description` — описание;
- `order_data` — дополнительные данные приказа;
- `status` — статус приказа.

Поддерживаемые типы приказов:

- `Прием на работу`;
- `Увольнение`;
- `Перевод`;
- `Отпуск`;
- `Изменение оклада`;
- `Премия`;
- `Взыскание`.

Поддерживаемые статусы приказа:

- `Не исполнен`;
- `Исполнен`;
- `Отменён`.

Ограничения:

- исполненный приказ нельзя редактировать;
- исполненный приказ нельзя удалить;
- повторное исполнение уже исполненного приказа не должно менять данные повторно.

### Transfer

Перевод сотрудника между подразделениями.

Поля:

- `transfer_id` — идентификатор перевода;
- `employee_id` — сотрудник;
- `old_department_id` — старое подразделение;
- `new_department_id` — новое подразделение;
- `transfer_date` — дата перевода.

Ограничения:

- сотрудника нельзя перевести в то же подразделение.

## 4. Основные сценарии использования

### UC-1. Авторизация пользователя

Предусловие:

- пользователь существует в таблице `Users`;
- учетная запись активна.

Основной сценарий:

1. Пользователь вводит логин и пароль.
2. Система хеширует введенный пароль.
3. Система ищет пользователя с указанным логином и хешем пароля.
4. Если пользователь найден и активен, система открывает главный экран.
5. Если пользователь не найден, система показывает ошибку.
6. Если пользователь найден, но неактивен, система показывает ошибку.

Ожидаемое поведение:

- `admin/admin` должен проходить авторизацию в демонстрационной базе;
- неверный пароль должен отклоняться;
- неизвестный логин должен отклоняться;
- неактивный пользователь не должен получать доступ к основному экрану.

### UC-2. Просмотр сотрудников

Основной сценарий:

1. Пользователь открывает раздел сотрудников.
2. Система загружает список сотрудников из базы данных.
3. Система отображает ФИО, дату рождения, дату приема, подразделение, должность, зарплату и статус.

Ожидаемое поведение:

- список сотрудников должен отображаться после входа пользователя с подходящей ролью;
- поиск должен фильтровать сотрудников по фамилии или имени.

### UC-3. Добавление сотрудника

Основной сценарий:

1. Пользователь открывает форму сотрудника.
2. Пользователь вводит ФИО, даты, подразделение, должность, зарплату и статус.
3. Система сохраняет сотрудника в базе данных.
4. Система обновляет таблицу сотрудников.

Ограничения:

- фамилия и имя не должны быть пустыми;
- зарплата должна быть числом;
- даты должны быть корректными.

### UC-4. Удаление подразделения

Основной сценарий:

1. Администратор выбирает подразделение.
2. Система проверяет количество сотрудников в подразделении.
3. Если сотрудников нет, подразделение удаляется.
4. Если сотрудники есть, система показывает ошибку.

Ожидаемое поведение:

- подразделение с сотрудниками не удаляется.

### UC-5. Создание и исполнение приказа

Основной сценарий:

1. Пользователь создает приказ.
2. Система сохраняет приказ со статусом `Не исполнен`.
3. Пользователь выбирает приказ и нажимает `Исполнить`.
4. Система применяет действие приказа к данным сотрудника.
5. Система меняет статус приказа на `Исполнен`.

Ожидаемое поведение:

- приказ на увольнение меняет статус сотрудника на `Уволен`;
- приказ на перевод создает запись в истории переводов;
- приказ на отпуск создает запись в отпусках;
- исполненный приказ нельзя удалить или изменить.

### UC-6. Перевод сотрудника

Основной сценарий:

1. Пользователь выбирает сотрудника.
2. Пользователь выбирает новое подразделение.
3. Система проверяет, что новое подразделение отличается от текущего.
4. Система создает запись о переводе.
5. Система обновляет подразделение сотрудника.

Ожидаемое поведение:

- перевод в то же подразделение отклоняется;
- история перевода сохраняется.

### UC-7. Просмотр отчетов

Система поддерживает отчеты:

- общая статистика;
- сотрудники по подразделениям;
- зарплатный фонд;
- график отпусков;
- сотрудники по стажу;
- должности и зарплаты.

Ожидаемое поведение:

- отчеты формируются на основе данных SQLite;
- отчеты не должны требовать ручной обработки данных пользователем.

## 5. Ограничения текущей версии

Текущая версия проекта находится в процессе рефакторинга.

Ограничения:

- основное Tkinter-приложение пока остается в `main.py`;
- часть бизнес-логики пока еще находится в GUI-коде;
- SQLite используется как локальное хранилище;
- запуск GUI в WSL требует настроенного графического интерфейса;
- автоматическая проверка проекта выполняется через тесты без запуска GUI.

## 6. Проверяемые требования текущего этапа

На текущем этапе должны выполняться следующие утверждения:

- исходный монолит сохранен в истории Git;
- smoke-тесты проходят и фиксируют базовое поведение базы данных;
- модуль `packages/core/storage.py` содержит класс `Database`;
- модуль `packages/core/auth.py` содержит логику авторизации;
- модуль `packages/core/models.py` содержит основные доменные модели;
- `main.py` не использует `hashlib` напрямую для авторизации;
- `packages/core` не импортирует Tkinter;
- все тесты проходят командой `make test`.
